# How knowledge retrieval (RAG) works in UDA-Hub

Code: `agentic/tools/knowledge_retriever.py` (retriever),
`agentic/agents/knowledge_retriever.py` (graph node),
`agentic/agents/specialist_base.py` (`search_knowledge_base` tool),
`agentic/agents/qa_reviewer.py` (grounding check).

## 1. Corpus

The `knowledge` table in `udahub.db` holds 29 CultPass articles: 4 supplied by
CultPass and 25 written for this project. They are generated by
`scripts/build_articles.py` into `data/external/cultpass_articles.jsonl` and
loaded by `02_core_db_setup.ipynb`. Each article has a title, agent-facing
guidance, a "Suggested phrasing" block and tags whose first tag is its
category (billing, subscription, reservation, technical, account, safety,
general, escalation, ...).

Articles are short (one policy each), so **one article is one chunk**.
Splitting them would separate a rule from its exceptions (e.g. "credit returned
only if cancelled more than 24 h before"). Each article gets a stable ref,
`KB-` plus the first six hex characters of its id, which agents cite.

## 2. Indexing

| Index | What is indexed | Where |
|---|---|---|
| Dense | `title + tags + content`, embedded with `text-embedding-3-small` | vectors cached in `knowledge_embeddings (article_id, model, content_hash, embedding)` |
| Sparse | BM25 (k1 = 1.5, b = 0.75) over the same text, **title and tags counted twice** | in memory, rebuilt when the article set changes |

The tokenizer lowercases, normalises multi-word phrasings to the vocabulary the
articles use (`log in` / `sign in` → `login`, `money back` → `refund`, `charged
twice` → `double charge`), drops stop words and applies light singularisation
(`queries → query`, `codes → code`).

The cache is keyed by a SHA-1 of the embedded text. Editing one article
re-embeds only that article, and a new retriever instance reuses the cache,
so the embedding API is not called again (both tested). The retriever
checks a cheap signature (`article_id`, `updated_at`) before every search,
so articles added at runtime are picked up without a restart.

## 3. Query construction and metadata

The query is the customer's latest message plus the classifier's one-line
`intent`. When the latest message is a short follow-up (fewer than 8 words,
e.g. "the samba one please"), the previous customer message is prepended so
the topic survives.

The classifier runs **before** retrieval, so its category is passed to the
search as metadata. `CATEGORY_TAGS` maps each ticket category to the article
tags that belong to it (e.g. `login_access → {login, password, access}`).

## 4. Search and fusion

1. BM25 scores every article.
2. The query is embedded and cosine similarity computed against every cached vector.
3. **Weighted Reciprocal Rank Fusion:** `score = 1.0/(60 + dense_rank) + 0.5/(60 + bm25_rank)`.
   Dense carries more weight because customers paraphrase ("the scanner won't read my ticket" →
   *QR Code Not Scanning*). BM25 contributes exact terms ("LGPD", "Procon", "QR").
4. **Category boost:** articles whose tags belong to the ticket's category get one more
   top-rank RRF term (`1.0/61`). This matters for phrasings the small embedding model gets wrong.
   For "I can't log in to my Cultpass account" it ranks *App Crashes* and *Not Receiving Emails*
   above *How to Handle Login Issues?* (cosine 0.37). With the `login_access` boost the login
   article comes first. The fused order is kept as the final ranking.
5. The top k (4 for the up-front retrieval, 3 for follow-up searches) are returned,
   dropping any article whose relevance is below 0.12 once at least one article is kept.

## 5. Confidence

Each article gets a **relevance** in [0, 1]:

* dense: `clamp((cosine - 0.22) / (0.58 - 0.22), 0, 1)`, plus 0.08 when the article is also in
  BM25's top 3 (lexical agreement) and 0.12 when it matches the ticket's category (metadata agreement)
* BM25-only fallback: `score / (score + 6)`

**Retrieval confidence** is the highest relevance among the returned articles.
The anchors 0.22 and 0.58 come from `evaluation/calibration.md`: 37 in-domain
questions with known answers (including 8 deliberately hard paraphrases) and 7
off-topic questions.

| | hybrid + category (production) | hybrid only | BM25 only |
|---|---|---|---|
| hit@1 / hit@3 | **36/37 · 37/37** | 33/37 · 37/37 | 24/37 · 31/37 |
| in-domain above the 0.35 gate | 36/37 (the exception is "talk to a real person", escalated earlier by the wants-human guardrail) | 36/37 | 35/37 |
| off-topic below the gate | 7/7 (highest 0.33) | 7/7 (highest 0.23) | 6/7 |

The **knowledge gate** (`UDAHUB_MIN_RETRIEVAL_RELEVANCE`, default 0.35) sits
between the two ranges. When the supervisor would route to the knowledge
resolver and confidence is below 0.35, the ticket is escalated instead
("no relevant knowledge article"). The system never answers from the model's
own knowledge.

## 6. Use in generation (grounding)

* The top articles are placed in the specialist's system prompt as
  `[KB-xxxxxx] Title relevance=…` followed by the content.
* Rule 1 of every specialist prompt: every policy, step, time frame or fee must come
  from an article or a tool result, and the refs used go in `cited_articles`.
* Specialists can call `search_knowledge_base(query)` for more evidence. The
  results join the set of citable articles for that turn.
* **The QA reviewer enforces grounding:**
  1. A resolved answer must cite at least one article.
  2. Every cited ref must have been retrieved in this turn. Invented refs are rejected.
  3. An LLM judge compares the reply with the cited articles and tool results.
  4. The final confidence is `0.4 × best cited relevance + 0.3 × specialist self-rating + 0.3 × judge score`.
     A resolved answer below 0.60 escalates.
* The escalation agent grounds its message on the escalation-policy article plus the
  team-specific article (e.g. blocked accounts → Trust & Safety, 2 business days).
* Citations are returned in `final["citations"]` and logged on the `resolution`
  event, so every reply can be traced to its sources.

## 7. Degraded modes

| Situation | Behaviour |
|---|---|
| No API key or `UDAHUB_OFFLINE=1` | BM25 only; still ranks reasonably (hit@3 31/37) but off-topic questions cannot be separated reliably by score, so this mode is for tests and offline development |
| Embeddings API error at query time | that search falls back to BM25; `dense_error` is logged on the `retrieval` event |
| Empty knowledge base or empty query | no articles, confidence 0 → escalation |

## 8. Memory retrieval uses the same machinery

Long-term memories are embedded with the same model and recalled by cosine
similarity (BM25 when embeddings are unavailable). See ARCHITECTURE.md section 7.
